## 🔴 严重

### ISSUE-01: `_resolve_enum_value` 对 float 输入值直接截断

- **位置**: `services/can_codec.py:285` — `_resolve_enum_value()`
- **现象**: 编码器对带分辨率的 float 字段（如 `365.1V` → `resolution=0.1`）编码时，输出字节与实际物理量不符。例如 BHM 报文 `绝缘监测允许总电压=365.1V`，期望数据 `43 0E`（LE: 3651），实际产出 `42 0E`（LE: 3650）。
- **根因**: `_resolve_enum_value` 中 `isinstance(value, (int, float))` 分支直接调用 `int(value)`，将 `365.1` 截断为 `365`。后续分辨率转换 `int(round(365 / 0.1)) = 3650`，丢失了 1 个 LSB。
- **影响范围**: 所有输入为 float 且带 `resolution` 字段的编码操作。GB/T 27930 的 BHM、BCL、CCS 等电压/电流字段都可能受影响（取决于输入值的小数部分是否被截断）。
- **修复**: 将 `int(value)` 改为直接 `return value`（保留 float），让分辨率转换层 `_pack_int_le/be` 处理完整的浮点值。`_resolve_enum_value` 的返回类型从 `-> int` 改为无类型约束。
- **状态**: ✅ 已修复 (2026-06-26)

### ISSUE-02: 浮点除法精度退化

- **位置**: `services/can_codec.py:256,266` — `_pack_int_le()` / `_pack_int_be()`
- **现象**: 即使 `_resolve_enum_value` 返回了正确的 float，`(value - offset) / resolution` 在 IEEE 754 浮点运算中可能产生低于目标整数的结果（如 `365.1 / 0.1 = 3650.9999999999995`），后续 `round()` 可能误舍入为整数减一。
- **根因**: `0.1` 无法在二进制浮点中精确表示，除法引入微小误差。
- **影响范围**: 所有分辨率不是 2 的整数次幂的字段编码场景。
- **修复**: 除法结果加 `1e-9` 安全裕量，确保轻微下偏差能被 `round()` 正确舍入。
- **状态**: ✅ 已修复 (2026-06-26)

## 🟡 中等

### ISSUE-03: 安世博协议 Byte0 组地址/信息类型 nibble 共享建模问题

- **位置**: `data/anshibo_1k040b.json` — 所有报文定义
- **现象**: Byte0 的高 4 位（组地址）和低 4 位（信息类型 MessageType）共享同一字节，但 JSON 中将"组地址"建模为 1 字节整数（`byte_start=1, length=1, data_type=int_be`），"信息类型"建模为位域（`bit_start=0, bit_len=4`）。编码时整字节字段先写入（`组地址=1` → 写入 `0x01`），位域字段再合并（`MessageType=2` → `byte |= 0x02`），最终得到 `0x03` 而非预期的 `0x12`。
- **期望行为**: 组地址应在 Byte0 高 nibble，即 `组地址=1` 应表达为 `0x10`，与低位 `MessageType` 组合为 `0x12` 或 `0x13`。
- **影响范围**: 安世博协议全部报文的编码功能。**解码不受影响**（解码不区分 nibble 语义，读取整字节 0x13 返回 19）。当前 P0 测试中安世博仅覆盖了解码向量。
- **建议修复方案**:
  1. 将"组地址"从 `int_be` 字段改为位域 `bit_start=4, bit_len=4`
  2. 或在 `_pack_int_be` 中增加 `nibble_shift` 属性支持
- **状态**: ⚠️ 待修复
