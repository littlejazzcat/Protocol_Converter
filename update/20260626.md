### 2.1 `models/loader.py` — 新增完整性校验

在文件末尾新增 `validate_integrity(protocol: ProtocolDefinition) -> list[str]` 函数。校验逻辑：

```python
def validate_integrity(protocol: ProtocolDefinition) -> list[str]:
    """校验协议定义的完整性，返回错误信息列表。
    检查项：
    1. 字段字节越界
    2. 同字节内位域重叠
    3. 报文标识符唯一性（按 message_matcher.type）
    4. data_type 一致性（bits 需 bit_start/bit_len，float 需 length=4）
    5. message_groups 引用完整性
    6. CAN ID Schema 位域不重叠
    7. 报文基础字段完整性（name/abbr 不空）
    """
```

检查项 3 根据 `message_matcher.type` 自动适配：
- `pf_based` → 检查 PF 不重复
- `data_field` → 检查 `(command_type, message_type)` 组合不重复
- `command_number` → 检查 command_number 不重复

### 2.2 `services/can_codec.py` — 2 个 Bug 修复

#### Bug 1: `_resolve_enum_value` float 截断

**位置**: 行 285-298

**原代码**:
```python
def _resolve_enum_value(self, field: FieldDef, value: Any) -> int:
    ...
    if isinstance(value, (int, float)):
        return int(value)  # BUG: int(365.1) = 365，丢失 0.1
```

**修复后**:
```python
def _resolve_enum_value(self, field: FieldDef, value: Any):
    ...
    if isinstance(value, float):
        return value  # 保留浮点，分辨率转换时处理
    if isinstance(value, int):
        return value
```

**影响**: 所有物理值含小数部分的编码操作之前都会先被截断，再参与分辨率转换。例如 `365.1V ÷ 0.1` 本应得到 raw=3651，因截断变成 `365 ÷ 0.1 = 3650`。

---

#### Bug 2: `_pack_int_le` / `_pack_int_be` 浮点精度

**位置**: 行 256 / 行 262

**原代码**:
```python
raw = int(round((raw - (field.offset or 0)) / field.resolution))
```

**修复后**:
```python
raw = int(round((raw - (field.offset or 0)) / field.resolution + 1e-9))
```

**影响**: IEEE 754 除法可能产生略低于目标整数的值（如 `365.1 / 0.1` 在某些场景下 = `3650.9999999999995`），`round()` 可能舍入为 `3650` 而非 `3651`。`+1e-9` 裕量确保轻微偏差不改变正确舍入结果。

### 2.3 `tests/conftest.py` — 新增共享 Fixtures

提供四套协议的独立 fixture 和 `all_protocols` 参数化 fixture，以及对应的 `(QueryEngine, CanCodec)` 引擎 fixture。

关键设计：
- `scope="module"` 一次加载复用，避免每条测试重复读 JSON
- `_load()` 辅助函数找不到文件时自动 `pytest.skip()`

```python

@pytest.fixture(scope="module")
def anshibo(): ...

@pytest.fixture(scope="module")
def sg_unified(): ...

@pytest.fixture(scope="module")
def infypower(): ...

@pytest.fixture(scope="module",
    params=["gbt27930_v1.1", "anshibo_1k040b", "sg_unified_v107", "infypower_v107"])
def all_protocols(request): ...
```

引擎 fixtures（协议 + 引擎配对）:
```python
@pytest.fixture(scope="module")
def gbt27930_engine(gbt27930): return QueryEngine(gbt27930), CanCodec(gbt27930)
# ... 其余三套同理
```

### 2.5 `tests/test_golden_vectors.py` — 已知向量测试 (28 条)

四个协议类，每类分别测试 encode 和 decode：

| 协议 | Encode | Decode | 关键覆盖 |
|------|--------|--------|---------|
| GB/T 27930 | 5 条 | 6 条 | LE 整数、负偏移电流(-400A)、枚举(恒流/恒压)、170=准备好了(0xAA)、位域(充电允许) |
| 安世博 | — | 5 条 | BE 4字节整数(mV)、枚举(开机/关机/线性关机) |
| 三统一 | 2 条 | 2 条 | LE 整数 + 多 bit 位域控制字(操作指令/电压范围/接触器) |
| 英飞源 | 4 条 | 4 条 | BE 4字节整数(mV/mA) + IEEE 754 浮点(500.0V/50.0A) |

**为什么安世博只有 decode 没有 encode？**
安世博协议 Byte0 的高 nibble（组地址）和低 nibble（信息类型）共享同一字节，当前 JSON 建模存在不一致（见 `issue/20260626.md` ISSUE-03）。编码时两个字段互相覆盖导致字节 0 错误，故暂时仅测试解码路径。
